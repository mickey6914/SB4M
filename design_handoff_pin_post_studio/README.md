# Handoff: Express Art Vibe Pin-Post Studio

## Overview

Express Art Vibe Pin-Post Studio is a Pinterest-first content generation tool. A seller pastes one
product listing link; the app pulls the listing images, asks four short questions (hero image, pin
volume, style direction, inspiration scenes), generates that many pin mockups with AI-written titles,
SEO descriptions and keyword sets, re-crops each approved pin for the other networks, and pushes the
finished batch into the user's existing **Content360** workspace, which owns the social accounts and
does the actual publishing.

The product's differentiator is a **single cross-network calendar** — Pinterest, Facebook and
Instagram posts for the same product on one month grid, with gap detection and per-post sync state.
Neither Pinsflow (the inspiration) nor Content360 offers this today.

Initial user: one seller running her own shops. Intended later market: Etsy/Shopify sellers.

## About the Design Files

The files in this bundle are **design references created in HTML** — prototypes showing intended
look and behavior, not production code to copy directly. `Express Art Vibe - Dashboard.dc.html`
is a single-file prototype with an inline-styled template and a small state class; it uses a custom
element (`image-slot`) purely so the reviewer can drop real product photos onto placeholders.

The task is to **recreate these designs in the target codebase's existing environment** (React,
Vue, SwiftUI, native, whatever is in use) using its established component library, routing and
styling patterns. If no codebase exists yet, choose the appropriate framework and implement there.
Do not ship the prototype HTML, and do not port `image-slot` — in production those slots are real
images fetched from the listing or generated by the image model.

## Fidelity

**High-fidelity.** Colors, typography, spacing, rules and interaction states are final and come
from the bound *Modernist* design system (tokens listed under Design Tokens). Recreate the UI
faithfully using the codebase's existing libraries. Copy in the prototype is intentional and
should be carried across verbatim unless a stakeholder changes it.

The exception is **data**: all listing data, pin titles, descriptions, keywords, calendar entries
and sync states in the prototype are illustrative. The AI copywriting on the review screen is real
(see Interactions), everything else is mock.

## Navigation model

A fixed 236px left sidebar with six destinations, and a single content pane to its right. There are
no nested routes; the wizard is a sequence of full-pane steps, not a modal.

| Sidebar item | Route | Notes |
| --- | --- | --- |
| Dashboard | `/` | Status surface + run starter |
| New run | `/run/product` | Enters the 5-step wizard |
| Review queue | `/review/:runId` | Badge shows count of pins awaiting review |
| Calendar | `/calendar` | The cross-network month |
| Library | `/library` | Past runs |
| Connections | `/connections` | Accounts + workspace rules |

The active item (and any wizard step, which highlights **New run**) is a solid accent fill with
white text at weight 600; inactive items are transparent with `--color-text` at weight 400.

## Interactions & Behavior

**Navigation.** Sidebar items and every in-page link/button navigate immediately; there are no
transitions between screens. Wizard Continue/Back move one step. "Generate pins" starts the run and
routes to the progress screen.

**Progress simulation → production.** The prototype advances a percentage on a 140ms interval
(+3 per tick) and auto-routes to review 600ms after reaching 100%. In production, replace this with
real job progress (poll or socket) and keep the four named stages, since users read them as an
explanation of where their money and time go.

**Selection rules.** Hero image is single-select. Scenes are multi-select capped at three, FIFO.
Volume is single-select and drives the review screen: pin cards past the volume are not rendered,
counts and asset totals recompute (`assets = volume × 3` for the three default crops), and the
selected pin index clamps.

**Crop tabs** change the aspect ratio of every card in the pin grid; the four-up preview panel
always shows all four regardless.

**Overlay position** is a three-way segmented control that re-anchors the overlay chip in all four
crop previews at once — the visual proof that overlays are re-placed per ratio rather than cropped.

**AI copywriting (real).** "Rewrite with AI" calls `window.claude.complete` with the product
description and the chosen scene names, asking for minified JSON: `title` (under 60 chars,
keyword-led, no emoji, title case), `desc` (two short warm sentences ending in " #ad"), and
`keywords` (exactly five lowercase 2–4-word Pinterest search phrases). The response is parsed by
slicing between the first `{` and last `}` to survive a stray markdown fence; the first three
keywords are pre-checked; the keyword note is replaced with "Written by Claude just now — 3 of 5
selected by default." Failures set an inline message, "Could not write that one — try again.", and
never throw. Concurrent calls are blocked while one is in flight.

In production this belongs on the server with an Anthropic API key — **a Claude subscription does
not cover programmatic calls.** Text generation is inexpensive at this volume; image generation for
the mockups is the real cost and needs a separate image model.

**Approve / reject.** Approve pin increments the approved count (clamped to volume) and advances the
selection; Reject advances without incrementing; Approve all sets approved to the full volume.

**Push to Content360.** Sets the pushed flag, routes to the dashboard, hides the queue warning and
shows the neutral-900 confirmation band. In production this is a real batch POST (see Integration).

**Not yet built.** Board pickers per network, pagination past six review cards, "Surprise me",
"Show 50 more" scenes, "Refresh boards", "Retry failed", and the brand switcher are present as
affordances without behavior. Decide with the stakeholder which are v1.

## Integration: Content360

Content360 is the user's existing scheduler and the system of record for publishing. Its API
**accepts post creation**, so a finished run is pushed directly — no CSV step. The workspace in
question is `34b00c5d-265d-4c55-92b7-ebbc57669d39`.

What the push needs to carry per post: the rendered asset at the network's crop, the caption, the
scheduled time, the target network, and for Pinterest the pin title, destination link and board.
Facebook needs its post type (post / reel / story). The app then tracks a per-post state machine —
**queued → pushed → published → failed** — surfaced as tags on the dashboard sync table and as
badges on calendar chips.

Division of responsibility to preserve: Pin-Post Studio owns ingestion, generation, copy, crops,
review and the cross-network plan. Content360 owns account auth, publishing and retries. Do not
rebuild an inbox, a link-in-bio or a media library.

## Scheduling rules (workspace level)

- Add **#ad** to every affiliate description; block a push that lacks it.
- Only schedule between 09:00 and 17:00.
- Never place the same product twice on one network on one day.
- Max posts per network per day (default 3).
- Default fan-out pattern and default overlay text.

These are set once in Connections, not per pin. Design assumption behind the calendar's density:
one brand, 30 pins/month fanned to three networks ≈ 90 posts ≈ 3/day, which fits a month grid with
2–3 chips per cell. Past ~6/day, make a week view the default.
